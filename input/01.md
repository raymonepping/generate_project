Recap: Linting Scripts & Automating Terraform Setup

Bridging Quality and Automation: Our Plan
Our goal for this final part was to integrate shell script quality checks into the project creation process. To do this, we developed a new script generate_project.sh which acts as a higher-level orchestrator. This script creates a new project repository (for any project type, not just Terraform), sets up some baseline files, and crucially, hooks in the sanity_check process from the start. Additionally, we created a helper script commit_gh.sh to streamline committing and pushing changes to GitHub with a single command. Here's how these pieces work together:

generate_project.sh: Accepts a project name and scaffolds a new folder with that name. It ensures Git and GitHub CLI are available, verifies you’re authenticated to GitHub, then creates the project directory and basic files (like a LICENSE and README). It copies in a standard .gitignore (if you have one globally) or creates a simple one. Next, if the commit_gh script is present (more on that soon), it makes it available in the project for convenience. Most importantly, if sanity_check is installed, generate_project.sh runs it on all relevant files (shell scripts, Python, JavaScript, Terraform files, Dockerfiles) to auto-format and lint them. It also installs a pre-commit Git hook that will run sanity_check on any staged files of those types before each commit. (This implements the very workflow we envisioned in Part I – automating quality checks on every commit.) Finally, the script initializes a Git repo locally, makes the first commit, and creates a new GitHub repository via CLI, pushing the initial commit to GitHub. In one go, you have a new project repository created, sanity-checked, and published.
commit_gh.sh: This is a simple Bash script to automate the git commit process. When run inside any Git repository, it will stage all changes, generate a timestamped commit message (like “27/06/2025 - Updated configuration and fixed bugs”), commit the changes, and push to the repo’s main branch on GitHub. It even ensures your SSH agent is running so the push will succeed. Essentially, it’s a shortcut for the common add/commit/push sequence, useful for quick iteration. While not a complex tool, it saves a bit of typing and standardises commit messages.
By combining generate_project.sh and commit_gh.sh with our Terraform setup script from Part II (create_tf_project.sh), we get a seamless workflow: create a new project with all quality safeguards, populate it with Terraform boilerplate, and effortlessly commit to source control. We’ll demonstrate this flow next.

Step-by-Step: Quality-Assured Terraform Project Creation
Let’s walk through an example of using these tools together. Suppose we want to start a new Terraform module or project called medium_transformers (perhaps for provisioning some infrastructure). We will use our new scripts to do it in record time, with high quality.

And the Git hook means we’ll keep it clean on every commit – no more forgetting to run ShellCheck or prettier, it’s enforced automatically.

2. Add Terraform Module Files
Now that the base project is set up and on GitHub, the next step is to populate it with a standard Terraform structure. Here we leverage the create_tf_project.sh script from Part II (which we have in our current directory) to add Terraform-specific files. We run:

$ ./create_tf_project.sh \
  --repository=medium_transformers \
  --type=public --providers="docker"
This command tells the script to set up the current folder as a Terraform project named medium_transformers, marked public (though the repo already exists, it will skip creating it again), and include the Docker provider configuration (for example, perhaps we plan to manage Docker resources via Terraform in this project). How It Works Under the Hood
It’s worth understanding a few key implementation details of our approach, to appreciate how the pieces click together:

Sanity Check Integration: The sanity_check tool we built earlier is the linchpin for quality enforcement. When generate_project.sh is run, it calls sanity_check --fix --report on any newly created files of supported types (shell scripts, Python, JS, Terraform, Docker). This means, for example, if the scaffolded Dockerfile or .tf files had any stylistic deviations, they’d be auto-corrected. The pre-commit Git hook that generate_project.sh installs is essentially a short script that filters staged files for known extensions (*.sh, *.py, *.js, *.tf, Dockerfile) and runs sanity_check --fix --quiet on them just before commit. This aligns perfectly with our Part I recommendation to include such a hook in project setup – we automated that step. The result is that every commit will have properly formatted code; for instance, your Terraform code will always be terraform fmt-ed and your shell scripts shfmt-ed and shellchecked before they go into version control. This drastically improves code quality and consistency across projects.
Project Generation and GitHub Automation: Aside from quality checks, generate_project.sh uses the GitHub CLI to create the remote repo for you. As long as you’ve done gh auth login beforehand, the script will handle repository creation (public by default, but easily adjustable). It even names the first commit message clearly and sets the main branch. In our example, the entire GitHub repo medium_transformers was created and populated in one go, which highlights how such automation can boost efficiency and enforce best practices simultaneously.
Terraform Structure Scripting: The create_tf_project.sh script (from Part II) is built to be idempotent and modular. Running it inside an existing Git repo is safe – it noticed the Git repo was already initialized and simply added files and made a commit. It uses a JSON file of provider definitions to insert provider blocks (we passed --providers="docker", so it likely added a Docker provider block in provider.tf and corresponding resource configurations via a helper script). It also configures a Terraform backend (if applicable) and versions, etc., providing a standard layout. By automating these steps, we ensure that our Terraform projects don’t miss any vital components (like a versions pin or an outputs file), and they remain consistent and reliable across the team.
Commit Convenience: The commit_gh.sh script might be the simplest piece of the puzzle, but it adds convenience. Particularly in this flow, after using create_tf_project.sh, we had a commit locally that needed pushing – commit_gh made it a trivial one-liner to handle that. Its use of a timestamped message is handy when doing frequent minor updates (so commit messages don’t all read “update” or “fix”). This script isn’t Terraform-specific at all; you can use it in any Git repo to quickly stage, commit, and push changes. It’s another little automation to reduce friction in the development process.
The beauty of this combined solution is that it’s generalizable. While we showcased it for a Terraform project (because infrastructure-as-code setups benefit greatly from such automation), the generate_project + sanity_check framework can kickstart any project – be it a Python library, a Node.js app, or a simple collection of Bash scripts – with an assurance of code quality. The sanity check tool supports multiple languages and can easily be extended as new linters or formatters emerge. This means no matter what technology your new project uses, you can begin with confidence that basic formatting and linting are taken care of.

Benefits of the End-to-End Approach
By integrating quality control into project initialization, we achieved several wins:

Consistent Project Standards: Every project begins life with the correct structure (thanks to templates and scripts) and conforms to coding standards from day one. This ensures consistency and reliability across projects, which is invaluable when multiple team members or teams are creating infrastructure code.
Time Savings: What used to be a sequence of manual steps — create repo, add README, copy license, initialize Terraform files, set up git, run linters, etc. — is now distilled into a couple of commands. Automating repetitive setup tasks significantly reduces setup time. Engineers can start coding the real logic or resource definitions within minutes, not hours.
Built-in Error Prevention: The inclusion of sanity checks means that common errors (like script syntax issues or Terraform syntax mistakes) are caught before the code ever runs in production or gets committed to source control. This early feedback loop enhances reliability (fewer bugs due to typos) and enforces good habits (you literally can’t commit code that fails the linting rules).
Seamless GitHub Integration: Because the process auto-creates a GitHub repository and pushes the initial code, collaboration can begin immediately. There’s no delay or separate step to set up remote repositories. This is very collaboration-friendly, as teams can jump straight into pulling the repo and contributing. It also aligns with DevOps best practices of version-controlling everything from the start.
Modularity and Flexibility: Our scripts are modular — for instance, you can use generate_project.sh to initialize any project, even if it’s not Terraform-related, or skip create_tf_project.sh if you don’t need Terraform files. We can easily adjust them to include other boilerplate as needed. The provider selection in the Terraform script means you can tailor each project to include only what you need (e.g., one project might include AWS and Consul providers, another just Docker), without editing the core logic. This flexibility makes the automation broadly useful.
CI/CD Readiness: Starting a repo with built-in linting and formatting means it’s CI/CD-ready. You can hook up CI pipelines to run sanity_check --summary (to fail on any lint issues) or terraform validate knowing the code is already in good shape. The consistency enforced locally will translate to fewer CI surprises, making continuous integration smoother.
