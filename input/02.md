Why Standardize Builds and Checks
Building container images and projects ad hoc leads to confusion. One team might tag images by hand, another uses custom scripts, and secrets or build artifacts might slip into repos. By contrast, a standardized pipeline ensures each image build:

• Uses the same toolchain: e.g. our pipeline uses Bash + HashiCorp Packer + Docker consistently .

• Applies predictable versioning: images follow semantic versioning tied to source code releases.

• Emits traceable metadata: Packer records who, when, and how each image was built . In fact, HCP Packer acts like a “tfstate” for images — storing only metadata, which gives a single source-of-truth for image versions .

• Is reproducible: since the build is codified in a Packer template, any developer or CI agent can rebuild the image identically.

In short, every image becomes auditable and debuggable. As we saw before, build_container.sh provides “a universal, one-command way to build a Docker image for any service, with best practices built in” . This means fewer inconsistencies and “no more bespoke build scripts” scattered across projects — leading to more reliability and easier deployment (even into environments like HashiCorp Nomad via Terraform ).

Pipeline Overview: Step by Step
Our pipeline combines techniques from earlier articles into one thread. The key steps are:

1. Project Bootstrap: Run a generate_project.sh script to create a new repo folder, copy in baseline files (e.g. README.md, LICENSE, a standard .gitignore), and initialize Git. This script also runs sanity_check on the new files (enforcing style/lint rules) and sets up a pre-commit hook for future checks .

2. Validate .ignore Files: Ensure critical patterns (like *.env, node_modules/, *.tfstate, etc.) are in .gitignore or .dockerignore. For example, using git check-ignore <file> can confirm that a sensitive file is indeed ignored by Git .

3. Initial Commit: After scaffolding, automatically stage all files and make the first commit. We use a helper script commit_gh.sh to add, commit with a timestamped message, and push to the remote Git repo .

4. Packer Build & Push: Use build_container.sh (our Packer-based builder) to generate a Docker image. This script reads your project’s metadata (like version), dynamically creates a Packer HCL template, runs packer build, and then tags and pushes the image to a registry (e.g. Docker Hub) . It tags by semantic version (and also :latest), so the new image myapp:2.4.0 is created and pushed alongside myapp:latest.

5. Scan: After building the image, we run scan_container.sh. This runs a suite of security tools to audit it: Hadolint (Dockerfile linter), Dive (layer inspector), Trivy and Grype (vulnerability scanners), Dockle (CIS benchmark linter), and Syft (to generate a SBOM) . Each tool’s findings are logged for review. This ensures the image is free of known CVEs or Docker anti-patterns.

6. Commit Updates: The scan script bumps a .image_version file and tags the new version . We then git add, commit, and push these changes (updating the version file and any other notes) using commit_gh.sh . This final commit ties the built image back to source control for full traceability.

Together, these steps turn “it works on my machine” into “it’s reproducibly built, audited, and recorded.”

Project Creation & Quality Checks
First, we bootstrap the project. The generate_project.sh script (introduced in our Terraform article ) accepts a project name and creates a new folder structure. It copies in any global .gitignore (or writes a basic one) along with LICENSE, README.md, etc . Crucially, it then runs our sanity_check utility on the initial files . For example, if your project has any .sh, .py, .js, .tf, or Dockerfile files, sanity_check will format and lint them right away (we built it to wrap tools like shfmt, shellcheck, black, eslint, terraform fmt, Hadolint, etc. ). This auto-formatting enforces consistent code style from the very first commit. The script also installs a Git pre-commit hook to run sanity_check on every staged file in future commits. As our previous post on shell script sanity explains, this approach reduces manual overhead and catches bugs early by checking code on-the-fly

After formatting, generate_project.sh initializes a Git repository, makes the first commit, and (if configured) creates a remote repo via the GitHub CLI and pushes the commit . We also bundle in a helper commit_gh.sh script that, when run later, will stage any changes and push with a standardized, timestamped message . This gives us a reproducible starting point: a clean repo with quality checks in place. (For example, it outputs something like “Running sanity_check… Initialized empty Git repository… Installing pre-commit hook…” as it runs .)

Finally in this stage, we double-check our ignore files. It’s easy to forget to include new file types in .gitignore or a .dockerignore. A quick way is to try git check-ignore on a file. As the Git docs note, this command will report the pattern that excludes a given pathname . In practice, you can git check-ignore -v secret.env to confirm it’s listed. Ensuring these ignore patterns keeps build artifacts (like .terraform/, node_modules/, etc.) and secrets out of Git and container contexts.

2. Packer-Based Image Build and Push
With the repo ready, we move to building the Docker image via Packer. Instead of a bare docker build, we use a dynamic Packer template for consistency . Our build_container.sh script (covered in detail previously) starts by reading version info from the project (e.g. a package.json or a .image_version file) and bumping it (by default the patch number) . It then generates a packer.pkr.hcl file on the fly, inserting the desired base image (gleaned from your Dockerfile’s FROM line) and various build instructions . For example, the template might use:

source "docker" "app" {
  image  = "node:18-alpine"   # detected from Dockerfile
  commit = true
}
build {
  sources = ["source.docker.app"]
  provisioner "file" {
    source      = "app/."       
    destination = "/app/"
  }
  # ... (possibly other shell provisioners) ...
  post-processor "docker-tag" {
    tags = ["${var.docker_repo}:${var.version}", "${var.docker_repo}:latest"]
  }
  post-processor "docker-push" {
    login = false 
  }
}
Finally, the script runs packer build on this template. Packer then pulls the base image, copies files, runs commands, and commits a new image layer – effectively doing the same as a docker build but in a more structured way. Critically, Packer’s post-processors (shown above) automatically tag the image with the new version (e.g. 2.4.0) and :latest, then push to Docker Hub. The snippet above ensures the final Docker image gets tagged properly and pushed without extra manual commands. If the CI environment is already logged in to Docker, login = false will use those creds. Thus in one step we get an image in the registry and an audit trail of its build.

One big advantage: if any step fails (say npm install or a Docker push), Packer will halt with an error. This structured failure mode is safer than chaining docker build && docker push in a shell. And thanks to HashiCorp Cloud Platform (HCP) Packer, metadata about this build is recorded in the cloud “artifact registry”. As noted earlier, HCP Packer doesn’t store the image itself, only metadata – yet this gives us a history of builds, as if there were a Terraform state file for images.

3. Scanning the Container Image
Once your Docker image is built and tagged — for example, using your build_image.sh workflow — the next essential step is to validate its integrity and security.

We do this using our enhanced scan_container.sh script, which replaces the earlier slim_container.sh. This updated tool performs vulnerability scanning and software bill-of-materials (SBOM) analysis using industry-standard tools:

🔍 Trivy for vulnerabilities (High/Critical only)
📦 Syft for SBOM
🚨 Grype for CVEs
🔬 Dive (optional with --full flag) for layer analysis
🛡️ Dockle (optional with --full flag) for best practices
./scan_container.sh --image repping/ubuntu_hardened:latest
Or for a deeper scan:

./scan_container.sh --image repping/ubuntu_hardened:latest --full
All output is:

Stored under a timestamped folder inside ./logs/<image>/<timestamp>/
Appended to sanity_check.md in Markdown format for easy sharing
This ensures that every image you tag and push is well-documented and meets your security baseline.

Conclusion
By chaining project scaffolding, code quality tools, Packer-based builds, and automated scanning, we get a unified pipeline that eliminates manual steps and blind spots. Every new project starts with clean code (thanks to sanity_check), a solid commit history, and an up-to-date .gitignore. Every Docker image is built via Packer so builds are uniform and logged. Every artifact is versioned and stored in a registry with traceability. And every image is slimmed and security-scanned before it ever reaches production.

This approach — combining Bash scripts with HashiCorp tools — is accessible for general DevOps use but also leverages powerful platforms. While we demonstrated it with Docker and HashiCorp Packer, the concepts apply universally. For example, you could replace Docker with Podman or integrate the outcome into HashiCorp Nomad or Kubernetes deployments. The key is the “why”: consistent, auditable pipelines that catch errors early and make deployments reproducible. Following these steps, your teams get reliable builds and greater confidence that “what was built is what will be deployed.”

Next Steps
By chaining these scripts together, we’ve built a clean, automated pipeline for container projects: a one-command setup creates your repo, enforces style, builds the image, scans for vulnerabilities, and pushes everything to GitHub. This ensures container hardening by default — lean images, consistent code formatting, and thorough CVE scans — with minimal manual effort.
